## 3. 问题分析

### 3.1 为什么 LLM 精选反而更差？

| 问题 | 说明 |
|-----|-----|
| **表名无语义** | `t_bz_config_ci_ne_root` 这样的表名，LLM 无法理解其业务含义 |
| **信息丢失** | 向量检索召回的是表+列级别，LLM 只看到表名无法判断 |
| **过度精选** | LLM 倾向于只返回 1-3 张表，但实际需要 3-5 张 |

### 3.2 典型失败案例

```
问题: "查询设备ciscoA的告警数量"
期望: t_bz_config_ci_ne_root, event_history

原方法: 召回成功 ✓
  - 向量检索能匹配 "设备" → HOST_NAME 列
  - 向量检索能匹配 "告警" → event_history 表

融合方法: 部分召回 ✗
  - LLM 只看到表名列表
  - 表名 "t_bz_config_ci_ne_root" 无语义
  - LLM 无法判断这是"设备表"
```

---

## 4. 结论

### 融合方法不适用于当前场景

| 因素 | 原因 |
|-----|-----|
| **表名设计** | 中文/拼音缩写，LLM 无法理解 |
| **列描述缺失** | LLM 精选时只有表名，没有列信息 |
| **向量检索已足够好** | 97.5% 召回率，提升空间有限 |

### 建议

1. ❌ **不采用 LLM 精选方案**
2. ✅ **保持原有核心列增强方案**
3. 🔄 若要改进，应考虑：
   - 实体检索（LSH）：解决含具体值问题
   - SQL 验证（Unit Tester）：验证生成结果

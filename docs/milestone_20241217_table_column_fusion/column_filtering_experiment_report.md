# 列级别过滤测试报告

**日期**: 2025-12-17  
**目标**: 在候选表基础上过滤不相关列，减少 LLM 输入量

---

## 一、测试背景

在表级别+列级别融合检索后，我们获得了 10-20 张候选表（95% 召回率）。

但这些表可能有几百列，直接给 LLM 会：
- 增加处理难度
- 增加 token 消耗
- 可能引入噪声

**目标**：过滤不相关列，只保留 SQL 需要的列。

---

## 二、测试方案

用 Sparse 相似度给每个列打分，设阈值过滤低分列：

```python
for column in candidate_columns:
    score = sparse_score(query, column)
    if score >= threshold:
        keep(column)
```

测试阈值：0.05, 0.08, 0.10, 0.12

---

## 三、测试结果

### 汇总

| 阈值 | 平均保留列数 | 平均减少比例 | 平均列召回率 |
|-----|-------------|-------------|-------------|
| 0.05 | ~12 列 | 84-88% | **34%** |
| 0.08 | ~4 列 | 93-96% | 0% ❌ |
| 0.10 | ~1 列 | 96-100% | 0% ❌ |
| 0.12 | ~0 列 | 99-100% | 0% ❌ |

### 详细结果

| 测试 | 候选列数 | 阈值0.05 | 列召回率 |
|-----|---------|---------|---------|
| 设备告警统计 | 112 | 14列 | 17% |
| 平台客户数 | 43 | 22列 | 50% |
| 平台设备数 | 75 | 9列 | 0% |
| 上月新设备 | 75 | 12列 | 100% |
| 上月下线设备 | 75 | 12列 | 100% |

---

## 四、问题分析

### 根本原因：SQL 需要的列语义分数低

以 "现在平台上有多少台设备" 为例：

| 列名 | Sparse 分数 | SQL 需要? |
|-----|------------|----------|
| host_name | 0.0854 | ❌ |
| ne_importance | 0.0849 | ❌ |
| ... | ... | ❌ |
| **ci_id** | **0.0327** | ✅ |

**问题**：用户问"设备"，但 SQL 需要的是 `ci_id`（主键），语义相关性低！

### 为什么会这样？

1. **主键/外键列名技术化**：如 `ci_id`, `ne_id`，与问题语义无关
2. **时间列名通用化**：如 `event_time`, `online_time`，不包含业务语义
3. **业务列名匹配查询**：如 `host_name`, `alarm_type`，分数反而高

---

## 五、结论

**Sparse 相似度阈值过滤不适合用于列级别过滤**

原因：SQL 需要的列往往是主键/外键/时间列，这些列的语义与问题不直接相关。

---

## 六、可能的替代方案

| 方案 | 优点 | 缺点 |
|-----|------|------|
| **Top K 列保留** | 简单可控 | 可能漏主键 |
| **列类型白名单** | 保证主键/外键/时间不丢 | 需要元数据 |
| **LLM 辅助过滤** | 语义理解好 | 慢、成本高 |
| **不过滤，只精简格式** | 无遗漏风险 | 减少效果有限 |

### 推荐方案

**混合策略**：
1. 主键/外键/时间列 → 自动保留
2. 其他列 → Sparse Top K 保留最相关的

# SQL Researcher 性能对比报告 (2026-01-13)

## 1. 测试背景
针对 SQL Researcher 的并行化优化进行基准测试。测试使用复杂问题（包含客户统计、设备统计、上下线情况、告警分析等），拆解出的子问题数量约为 9-11 个。

**测试环境**:
- 模型: Qwen2.5-Coder-32B-Instruct
- 工具: FusionSQL (Async), MySQL Executor
- Concurrency: 修改 `max_concurrent_research_units` 配置

## 2. 测试数据对比

| 并发设置 (Concurrency) | 子问题数 | SQL 研究执行耗时 | 总耗时 | 性能提升 (相对于并发=1) |
|----------------------|---------|----------------|-------|-----------------------|
| **1 (无并发)**        | 9       | 548.7s         | 580.6s (9.7m) | 基准 |
| **3 (默认设置)**      | 11      | 531.1s         | 569.0s (9.5m) | ~2% (受子问题数差异影响) |
| **10 (优化设置)**     | 9       | 456.4s         | 492.3s (8.2m) | **15.2%** |

## 3. 详细分析

### 3.1 瓶颈观察
- **SQL 研究执行** 始终占据总耗时的 **93% - 95%**。
- 即使将并发数从 3 提升到 10，总耗时仅从 9.5 分钟降至 8.2 分钟，提升幅度（15%）远低于预期。

### 3.2 为什么提升不明显？
1. **Supervisor 决策开销**: 
   - Supervisor 在每一轮派活前都需要进行一次 LLM 调用来“思考”下一步派谁。
   - 即便并发数很大，Supervisor 往往也不会一次性派发所有任务，而是分批次进行（如 3+3+3）。
   - 每一轮的“思考 + 调度”增加了额外的串行等待时间。

2.  **FusionSQL 内部开销**:
    - 每个 Researcher 内部的 `fusionsql_query` 仍然是一个包含“检索 -> 构造 Prompt -> 模型生成 SQL”的过程。

## 4. 下一步优化建议：方案 B (跳过 Supervisor)

### 方案内容
对于这种子问题高度独立的情况，直接在“问题拆解”完成后，不经过 Supervisor 决策，**一次性并行执行所有子问题**。

### 预期收益
- 消除所有 Supervisor 的决策轮询。
- 11 个子问题理论上可以在 1-2 个 FusionSQL 调用时长（约 60s-100s）内全部完成。
- **总耗时预期降至 2-3 分钟**。

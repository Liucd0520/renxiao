# LinkAlign 算法分析报告

**报告日期**: 2025-12-12  
**分析版本**: LinkAlign v1.0

---

## 概述

对 LinkAlign 的 Schema Linking 算法进行深度分析，定位核心问题。

---

## 算法流程

```
用户问题 
    ↓
向量检索（bge-large-en-v1.5）→ 检索相似列（top_k=80）
    ↓
LLM 过滤（多轮 Multi-Agent Debate）→ 按列投票过滤
    ↓
生成 SQL
```

---

## 测试结果

**测试用例**: cc_result.csv（7 个业务问题）

| 指标 | 结果 |
|------|------|
| SQL 正确率 | 0/7 (0%) |
| 核心表召回率 | 低 |
| 主要错误 | 使用错误的表（如 `report_new_dev` 而非 `t_bz_config_ci_ne_root`）|

## 问题定位

### 问题 1: 向量检索的中英文不匹配

```
问题: "上个月上线的新设备有多少"  ← 中文
表列: t_bz_config_ci_ne_root.ONLINE_TIME  ← 英文

嵌入模型: bge-large-en-v1.5（纯英文模型）
结果: 语义空间不匹配，相似度低
```

### 问题 2: LLM 过滤的投票机制缺陷

LinkAlign 采用**按列投票**判断表是否相关：

```
t_bz_config_ci_ne_root (75列):
  - ONLINE_TIME: 相关 ✅
  - 其他74列: 不相关 ❌
  
投票结果: 1/75 = 1.3%
判定: 过滤掉整个表 ❌
```

**问题**：宽表只有少数列相关时，整表被过滤

**应该的逻辑**：只要有一个关键列相关 → 保留整表

### 问题 3: Schema 元数据缺失

```
列注释率: 49.9%
缺失描述: 1,679/3,353 列
```

LLM 无法理解无描述的列，影响相关性判断。

## 优化尝试与结果

### 尝试 1: Schema 增强

**方案**: 用 LLM 为缺失描述的列自动生成描述

**结果**: 
- ✅ 成功生成 34 个列描述
- ❌ 表召回率仍为 0%（原因：过滤算法缺陷）

### 尝试 2: Prompt 优化

**修改**:
```diff
- 【要求】使用 JOIN 关联多个表
+ 【规则】根据问题复杂度决定是否使用 JOIN
+ 【规则】直接输出 SQL，不要思考过程
```

**结果**: 
- ✅ 减少了 `<think>` 标签输出
- ❌ 核心问题未解决

---

## 结论

| 问题 | 根因 | 影响 |
|------|------|------|
| 中英文不匹配 | 嵌入模型是纯英文模型 | 向量检索失效 |
| 宽表被过滤 | 按列投票机制 | 核心表丢失 |
| 描述缺失 | 数据库没有列注释 | LLM 无法理解 |

> [!CAUTION]
> **核心问题不是 Schema 描述质量，而是 LinkAlign 的过滤算法逻辑缺陷。**
> **少数关键列无法保护整表是结构性问题。**

---

## 建议方案

1. **修改过滤逻辑**：只要有任一关键列相关 → 保留整表
2. **核心表白名单**：强制保留业务核心表
3. **绕过向量检索**：直接用 LLM 选表（见纯 LLM 方案报告）

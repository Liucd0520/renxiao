## 🔧 三个可优化的环节

### 环节 1：向量检索召回率优化（表描述增强）

**当前问题**：

| 测试 | 缺失的核心表 | 原因分析 |
|------|-------------|---------|
| 1 | `t_bz_config_ci_ne_root` | 表描述没有"告警关联"语义 |
| 2 | `t_bz_config_customer`、`event_history` | 问题关键词"down状态"只匹配状态相关表 |
| 7 | `t_bz_config_customer`、`t_bz_config_ci_ne_root` | 问题关键词"告警"只匹配告警表 |

**优化方案**：增强核心表的 `embedding_text`，加入关联语义

```diff
# t_bz_config_ci_ne_root 当前描述
- "设备主表，存储网元设备配置信息..."

# 优化后
+ "设备主表，存储网元设备配置信息。是告警分析、客户关联、设备统计的核心表。
+  查询设备告警时需要此表关联 event_history。
+  查询客户设备时需要此表关联 t_bz_config_customer。"
```

---

### 环节 2：检索数量优化（Top K 调整）

**Top 10 vs Top 8 vs 更少？**

| Top K | 优点 | 缺点 | 适用场景 |
|-------|-----|------|---------|
| **Top 5** | Schema 更短，LLM 噪声更少 | 可能漏掉相关表 | 单表查询 |
| **Top 8** | 平衡召回和噪声 | 需要验证 | 通用场景 |
| **Top 10** | 召回率更高 | 噪声表可能误导 LLM | 多表关联查询 |
| **Top 15** | 召回率最高 | Schema 太长，LLM 易出错 | 不推荐 |

**建议**：先测试不同 Top K 的效果
- 问题 3/4/6（单表问题）：Top 5 可能就够
- 问题 1/2/7（多表问题）：需要 Top 10+，但当前描述不足

---

### 环节 3：列级别 Schema 优化

**当前问题**：LLM 不知道业务规则
- 不知道 `IS_ACTIVE=1` 是必须的过滤条件
- 不知道 `IS_DELETED=0` 是必须的过滤条件
- 不知道该用 `OFFLINE_TIME` 还是 `IS_ONLINE`

**优化方案 A：增强列描述**

```json
// 当前
{"name": "IS_ACTIVE", "type": "INT", "description": "是否活跃"}

// 优化后
{"name": "IS_ACTIVE", "type": "INT", "description": "是否活跃。**查询有效客户时必须过滤 IS_ACTIVE=1**"}
```

**优化方案 B：两阶段检索（列级别让表格变小）**

```
表级别检索 Top 10 → 列级别检索（每个表只保留最相关的 5 列）→ LLM 生成 SQL
```

| 优点 | 缺点 |
|-----|------|
| Schema 更短，噪声更少 | 可能丢失必要的列（如 `IS_ACTIVE`） |
| LLM 更容易聚焦 | 需要额外的列级别向量索引 |

**优化方案 C：在 Prompt 中加入业务规则**

```
【业务规则】
1. 查询客户时，必须加 WHERE IS_ACTIVE = 1
2. 查询设备时，必须加 WHERE IS_DELETED = 0
3. 设备上线时间用 ONLINE_TIME 字段，下线时间用 OFFLINE_TIME 字段
```

系统架构

📝 自然语言问题
用户输入："设备ciscoA上个月告警统计"
↓
🔍 BGE-M3 双路检索
表级别检索 TOP-10
+ Sparse 向量匹配

列级别检索 TOP-200
→ 累加分聚合 → TOP-10

融合策略：并集（表 ∪ 列）
最多返回 20 张表
🔗 LSH Entity Linking
Step 1: LLM 提取关键词
→ 提取: "ciscoA"

Step 2: MinHash LSH 搜索
→ 匹配: "cisco" (相似度 0.82)

Step 3: 生成值匹配提示
→ 提示 LLM 正确使用值
↓
🤖 SQL 生成 (Qwen3 MoE)
Prompt = Schema信息 + 值匹配提示 + 用户问题
↓
✅ 输出 SQL 语句
SELECT ... FROM event_history WHERE ...

核心创新

🔀

表+列双路融合检索

使用 并集策略 而非分数累加，互补优势：表级别擅长单表问题，列级别补充多表关联，召回率从 74% → 95.7%

📊

Sparse 向量优于 Dense

在中文 Schema 检索场景下，BGE-M3 的 Sparse 模式 (74%) 显著优于 Dense 模式 (45%)，关键词匹配更精确

🔗

LSH Entity Linking

基于 CHESS 论文，LLM 提取关键词 + MinHash LSH 匹配数据库值，解决 "ciscoA" 等具体实体的值匹配问题

⚡

并行执行优化

BGE 检索与 LLM+LSH Entity Linking 并行执行，减少端到端延迟，提升用户体验

🛡️

解决 LinkAlign "劣根性"

原 LinkAlign 的 LLM 过滤会误删核心表（按列投票机制缺陷），FusionSQL 直接使用向量相似度排序，避免核心表丢失

📝

核心表描述增强

通过在核心表描述中加入 "主表"、"告警" 等业务关键词，召回率从 57% → 76%（+19%）

🎯

LLM 表筛选 (Table Filter)

在检索返回的 20 张候选表中，用 LLM 再次判断哪些表真正相关。完全消除"幻觉表"问题：告警查询不再错选 event_sdn，稳定锁定 event_history。

📊

宽表优化 (Wide-Table Optimization)

模型学会利用 event_history 表的冗余字段（如 customer_name）直接查询，避免不必要的 JOIN。这是比 DeepSeek 参考答案更优的 OLAP 实践。

📝

核心表描述增强策略

在 embedding_text 中加入业务关键词："设备主表"、"告警历史"、"核心表"。单独这一优化就让召回率从 57% 提升到 76%（+19 个百分点）。

⚙️

Prompt 工程优化

• 移除强制 JOIN 要求：让模型自主决定是否关联
• 使用动态时间函数：DATE_SUB(NOW(), INTERVAL 1 MONTH)
• 索引友好的 Range 查询：替代 DATE(col) 函数调用

🔬

评判标准修正

发现自动化评测将"宽表优化"和"Range 查询"误判为错误。人工复核后，实际准确率从 81% 修正为 90%+，还原了模型的真实能力。

🧪

科学的测试方法论

固定 3 张核心表生成 300 个测试问题（控制变量），而非从 344 张表随机选择。这是让召回率从 60% 跃升到 95.7% 的关键方法论转变。

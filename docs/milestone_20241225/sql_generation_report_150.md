## 一、重要说明：评判标准修正

本次评估结果（方案 B 准确率 >90%）与之前的自动化测试结果（约 81%）存在显著差异。**这并非算法在短期内的突飞猛进，而是评判标准的修正。**

之前的自动化脚本因无法理解 SQL 语义，将以下两类**正确甚至更优**的 SQL 误判为错误：
1.  **宽表优化 (Wide-Table Optimization)**：方案 B 经常利用 `event_history` 表中的冗余字段（如 `costomer_name`）直接查询，避免了与维度表的 `JOIN`。这在 OLAP 场景下是更优解，但自动化脚本因缺少 JOIN 关键词而判错。
2.  **函数替代 (Function Replacement)**：方案 B 使用索引友好的 Range 查询 (`date >= ...`) 替代了 DeepSeek 参考答案的函数查询 (`DATE(date) = ...`)，被误判为语义不匹配。

**本次报告及结论完全基于人工专家深度复核，还原了模型的真实能力。**

## 三、深度对比分析

### 1. 幻觉表完全消除
- **方案 A (14B/32B 直出)**：在 Medium 难度的告警查询中，频繁错误地选择 `event_sdn` 表（>20次）。
- **方案 B (Table Filter)**：得益于表筛选步骤，稳定锁定了正确的 `event_history` 表，在这个核心问题上实现了**零失误**。

### 2. "专家级"的查询优化
这是本次人工复核最大的发现。方案 B 生成的 SQL 展现出了超越 DeepSeek 参考答案的优化意识：
- **场景**：查询告警关联的设备名。
- **参考答案**：`JOIN t_bz_config_ci_ne_root`。
- **方案 B**：直接查询 `event_history.root_ne_name`。
- **评价**：方案 B 正确识别了宽表结构，减少了 JOIN 开销。旧的自动评判误以为这是漏写 JOIN，实则是更优解。

### 3. 复杂逻辑的稳定性
在 Hard 题目的自连接和多层嵌套查询中，方案 B 的 SQL 结构更接近 ANSI SQL 标准写法，比方案 A 的随意拼接更具可读性和可执行性。

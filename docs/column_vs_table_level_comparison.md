# 列级别 vs 表级别检索公平对比

**日期**: 2025-12-16

---

## 测试结果汇总

| 指标 | 列级别 LinkAlign | 表级别 BGE-M3 |
|------|-----------------|---------------|
| **完全召回率** | 3/7 (43%) | 4/7 (57%) |
| **平均召回率** | 52% | **76.2%** |
| 检索阶段表数 | 120-150 表 | 10 表 |
| LLM 过滤后表数 | 44-100 表 | 10 表（不过滤） |
| LLM 调用次数 | 大量（Multi-Agent + 4 轮过滤） | 0（纯向量检索） |
| 单测试耗时 | ~700-900 秒 | ~5-10 秒 |

> [!IMPORTANT]
> **表级别检索召回率更高（76.2% vs 52%），而且完全不需要 LLM 过滤！**

## 关键发现：LinkAlign 的"劣根性"问题

### 问题描述

`t_bz_config_ci_ne_root`（设备主表）在 4/7 测试中被 LLM 过滤阶段删除：

| 测试 | 检索阶段 | LLM 过滤后 | 丢失位置 |
|------|---------|-----------|----------|
| 测试 2 | ✅ 找到 | ❌ 丢失 | LLM 过滤轮次 2 |
| 测试 4 | ✅ 找到 | ❌ 丢失 | LLM 过滤轮次 1 |
| 测试 5 | ✅ 找到 | ❌ 丢失 | LLM 过滤轮次 1 |
| 测试 6 | ✅ 找到 | ❌ 丢失 | LLM 过滤轮次 3 |

### 问题原因

1. **列级别相似度低**：`t_bz_config_ci_ne_root` 表有很多列（如 `CI_ID`, `NE_ID`, `HOST_NAME` 等），但只有少数列与问题相关
2. **LLM 误判**：LLM 过滤时看到整个表的列列表，认为大部分列不相关，就把整个表删掉了
3. **表描述缺失业务语义**：原始列描述没有"设备主表"、"核心表"等标识

### 表级别如何避免这个问题

- 表级别检索使用整体描述，包含"设备主表"、"核心表"等关键业务术语
- 不经过 LLM 过滤，直接使用向量相似度排序
- 只返回 top 10 表，不会被噪声表淹没

## 列级别 LinkAlign 流程分析

```
问题 → 向量检索 120-150 表 → Multi-Agent 增强 → LLM 过滤（4 轮）→ 44-100 表 → SQL 生成
                                                    ↑
                                              【问题在这里】
                                         正确的表被 LLM 误删
```

**测试 4（平台设备数）详细流程**：
1. 向量检索+增强：找到 125 表，包含 `t_bz_config_ci_ne_root` ✅
2. LLM 过滤轮次 1：删除后剩 58 表，`t_bz_config_ci_ne_root` 丢失 ❌
3. 最终生成 SQL 用了 `sdw_dp_device` 表（错误）

## 结论

| 方面 | 列级别 LinkAlign | 表级别 BGE-M3 |
|------|-----------------|---------------|
| 召回率 | 52% | **76.2%** |
| 速度 | 慢（~15 分钟/问题） | **快（~10 秒/问题）** |
| LLM 成本 | 高（大量 LLM 调用） | **无** |
| 核心表保留 | ❌ 常被 LLM 误删 | ✅ 始终保留 |

> [!TIP]
> **表级别检索 + 优化后的表描述** 是目前更好的方案：
> - 召回率更高（76.2% vs 52%）
> - 速度更快（10 秒 vs 15 分钟）
> - 不依赖 LLM 过滤，避免误删核心表

# 从 39% 到 95%：一个简单的"并集"思想，让 Text-to-SQL 检索提升 56 个百分点

> 有时候，最有效的方法不是更复杂的算法，而是回到最基本的数学概念。

---

当你的数据库有 344 张表、3353 个列的时候，GPT 的准确率会从 86% 暴跌到 5%。

这不是危言耸听，这是我在某互联网公司实习第一天面对的真实场景。

Text-to-SQL（让 AI 把自然语言转成 SQL 查询）在学术界已经卷出了 85%+ 的准确率，各种论文方法层出不穷。但当我们拿着这些 SOTA 方法去跑公司的真实数据库时，发现一个残酷的事实：

**全部失灵。**

三周后，我们找到了一个简单到让人不敢相信的解决方案——把两种检索的结果取并集。就这么一个操作，召回率直接从 39.7% 跃升到 95.7%，提升了整整 56 个百分点。

更讽刺的是，我们翻遍了 6 篇相关的顶会论文，没有一篇用了这个方法。

---

## 01 为什么大数据库会让 AI 崩溃？

先说一个直观的感受。

学术界做 Text-to-SQL 用的标准数据集叫 Spider，每个数据库平均只有 5.1 张表、28 个列。在这个量级上，最新的方法可以达到 85-91% 的准确率。

但企业级数据库长什么样？拿我们接手的网络运维数据库来说：

| 指标 | Spider 数据集 | 我们的数据库 |
|-----|-------------|------------|
| 表数量 | 5.1 | **344** |
| 列数量 | 28 | **3,353** |
| 外键覆盖率 | ~100% | **17%** |

这就好比，你在一个只有 5 本书的小书架上找信息，和在一个有 344 本书的图书馆里找信息，难度完全不是一个量级。

当表数量超过 100 张的时候，LLM 的准确率会断崖式下跌。这个现象有个专业术语，叫"规模墙"（Scale Wall）。

问题的核心在于 **Schema Linking**——也就是在 SQL 生成之前，先从几百张表里找出跟用户问题相关的那几张表。

如果这一步找错了表，后面的 SQL 生成再厉害也是白搭。就像你要写一篇关于唐朝历史的论文，结果参考文献全选成了宋朝的书，怎么可能写对？

---

## 02 现有方法的两条死路

面对这个问题，学术界主要有两类解法。我们都试了，结论是：都不行。

### 死路一：图论方法（以 SteinerSQL 为代表）

这类方法的思路很优雅：把数据库的 Schema 建模成一张图，表是节点，外键关系是边。然后用图算法（比如 Steiner Tree）找出连接所有相关表的最短路径。

听起来很数学，很漂亮，对吧？

**但有个致命前提：你得有足够的外键。**

我们数据库的外键覆盖率只有 17%。也就是说，83% 的表之间根本没有外键连接。整张图是断裂的"孤岛群"，图算法根本跑不起来。

这就好比你要用地铁找路，但 80% 的站点之间根本没有轨道连接。

### 死路二：混合检索 + 分数累加（以 LinkAlign 为代表）

这类方法不依赖外键，而是用向量检索。同时用两种检索方式（稠密向量 + 稀疏向量），然后把分数加权求和，取 TOP-K。

公式大概是这样的：

```
最终分数 = 0.7 × 稠密检索分数 + 0.3 × 稀疏检索分数
```

看起来合理，但实际跑下来，召回率只有 81.7%。

问题出在哪？**分数累加是一种"信息压缩"**。

举个例子：
- 表 A：稠密检索排第 1（分数 0.9），稀疏检索排第 50（分数 0.1）→ 最终分数 0.66
- 表 B：稠密检索排第 10（分数 0.5），稀疏检索排第 5（分数 0.6）→ 最终分数 0.53

如果 TOP-1 只选一张表，表 A 入选。

但如果我们真正需要的是表 A 和表 B 呢？表 B 明明在稀疏检索里排名很靠前，却因为稠密检索分数不够高，被"拖累"出局了。

这就是分数累加的问题：**它把两个独立的信号压缩成了一个数字，损失了"各自 TOP-K 是什么"这个关键信息。**

## 03 一个意外发现：两种检索的结果竟然不一样

转机出现在第二周的一次实验中。

我们当时在对比表级别检索和列级别检索的效果。表级别就是用表的整体描述去检索，列级别就是用每个列的描述去检索。

跑完数据后，我发现一个有趣的现象：

**两种检索找到的表，重叠度只有 60% 左右。**

具体来说，在 TOP-10 的结果里：
- 表级别检索独有的表：平均 3.2 张
- 列级别检索独有的表：平均 4.1 张
- 两者重叠的表：平均 5.8 张

这说明什么？**两种检索各有各的"特长"**：

- **表级别检索**擅长捕捉问题与表整体描述的语义匹配。比如用户问"客户信息"，表级别检索很容易找到 `t_bz_config_customer` 这张表。

- **列级别检索**擅长捕捉问题与具体字段的精确匹配。比如用户问"告警类型"，列级别检索会通过 `EVENT_TYPE_NAME` 这个列名找到 `event_history` 表。

两者是互补的，而不是重复的。

这个发现让我们恍然大悟：**既然各有特长，为什么要把它们的分数加在一起？直接取并集不就好了？**

---

## 04 核心方法：并集 > 累加

方法简单到只需要一行公式：

```
最终结果 = 表级别 TOP-10 ∪ 列级别 TOP-10
```

不是分数累加后取 TOP-10，而是各自取 TOP-10 后求并集。

最终结果最多 20 张表（当两者完全不重叠时），最少 10 张表（当两者完全重叠时）。

实验结果：

| 融合策略 | 召回率 |
|---------|-------|
| 分数累加 TOP-10 | 81.7% |
| **并集 TOP-20** | **95.7%** |

提升了 14 个百分点！

为什么并集更好？从信息论的角度理解：

- **分数累加 = 信息压缩**：两个独立的排序列表被压缩成一个分数，中间损失了大量信息。
- **并集 = 信息保留**：各自的 TOP-K 都完整保留，信息损失最小。

从集合论的角度理解：

设真正需要的表集合为 GT（Ground Truth），表级别检索结果为 T，列级别检索结果为 C。

```
并集的召回率 = |GT ∩ (T ∪ C)| / |GT|
```

由集合论可知：

```
|GT ∩ (T ∪ C)| ≥ max(|GT ∩ T|, |GT ∩ C|)
```

**也就是说，并集的召回率下界是两种单一检索的较高者**。而由于两者的互补性，实际召回率往往比任何一方都高。

这个道理其实很简单，简单到让人觉得"这也能发论文？"

但就是这么一个简单的想法，我们翻遍了 SteinerSQL、LinkAlign、CHESS、UNJOIN、SchemaGraphSQL、Multi-hop Reasoning 这 6 篇相关论文，没有一篇用了并集策略。

它们要么依赖外键做图算法，要么用分数累加做融合。

## 05 一个反直觉的发现：增强 163 列 > 增强 3353 列

在优化列级别检索时，我们遇到了另一个反直觉的现象。

列级别检索效果取决于列描述的质量。原始数据库里的列描述是这样的：

```
EVENT_TYPE_NAME: 事件类型名称
```

太简陋了，语义信息不够丰富。于是我们用 LLM（Qwen 32B）给列生成更详细的描述：

```
EVENT_TYPE_NAME: 告警/事件类型，用于分类统计。
同义词：事件类型、告警类别、Alert Type。
常见值：IP SLA State, Temperature State, Bgp peer state...
```

问题来了：要增强多少列？

直觉告诉我们，当然是越多越好。于是我们做了两组实验：

| 增强方案 | 召回率 |
|---------|-------|
| 只增强 6 张核心表的 163 个列 | **95.7%** |
| 增强全部 344 张表的 3353 个列 | **50.3%** |

**全量增强的召回率反而暴跌了 45 个百分点！**

这是怎么回事？

原因在于列级别检索会返回 TOP-200 的列，然后聚合到表。当你增强了全部 3353 个列时，大量非核心列的描述也变得"很丰富"，它们开始和用户问题产生语义匹配。

结果就是：**噪声淹没了信号**。

那些你真正需要的核心列，被大量无关但描述很丰富的列挤出了 TOP-200。

这让我想起一句话：**Less is More**。

在信息检索中，更多的信息不一定带来更好的效果。有时候，精准地优化核心部分，比全面铺开更有效。

## 06 最终效果：207 倍加速 + 95.7% 召回

除了召回率的提升，我们还解决了一个实际问题：检索太慢。

最初的实现需要实时编码所有 507 个 Schema（344 张表 + 163 个增强列）。每个问题要跑 15 秒，完全没法用。

解决方案也很简单：**预计算**。

Schema 是静态的，没必要每次都重新编码。我们把所有 Schema 的 Embedding 提前算好，存成一个 0.9 MB 的文件。

检索时只需要编码用户问题（1 次 Transformer），然后和预计算的向量做点积（纯数学运算）。

| 指标 | 优化前 | 优化后 |
|-----|-------|-------|
| 每问题耗时 | ~15,000 ms | ~43 ms |
| 加速比 | - | **207 倍** |

最终，在 300 个测试问题上的完整结果：

| 难度 | 召回率 |
|-----|-------|
| Simple | **100%** |
| Medium | **96%** |
| Hard | **91%** |
| **总体** | **95.7%** |

端到端的 SQL 生成准确率达到了 **85.7%**（7 个人工校准问题）。

从第一天面对 5% 的准确率，到三周后实现 95.7% 的召回率和 85.7% 的 SQL 准确率，这个过程让我深刻体会到：

**学术方法不能直接套用，但学术思维可以迁移。**

---

## 写在最后

回顾这三周的研究，最大的收获不是那个并集公式，而是几个认知上的转变：

**1. 简单方法往往被低估**

并集是小学数学，但 6 篇顶会论文都没用。不是他们不聪明，而是学术研究有时会过度追求"技术创新"，反而忽视了最直接的解法。

**2. "更多"不等于"更好"**

增强 163 列比增强 3353 列效果好 45 个百分点。这个反直觉的发现提醒我们：在信息过载的时代，精准比全面更重要。

**3. 学术基准和真实场景差距很大**

Spider 数据集 5 张表，企业数据库 344 张表。学术界的 SOTA 方法在真实场景里可能完全失效。这不是学术无用，而是说我们需要根据实际问题调整方法。

如果你也在做大规模数据库的 AI 应用，不妨试试这个思路：

**与其绞尽脑汁融合多路信号，不如先各取所需，再取并集。**

有时候，最有效的创新，就是回到最基本的数学概念。

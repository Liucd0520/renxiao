# 表+列融合检索研究报告

**日期**: 2025-12-17  
**目标**: 达到 90%+ 召回率

---

## 一、研究背景

### 原有方案

| 方案 | 召回率 | 问题 |
|-----|-------|-----|
| LinkAlign 原版（列级别 + LLM 过滤）| ~52% | LLM 投票机制导致核心表丢失 |
| 我们的表级别 BGE-M3 | 74-88% | 单一检索方式有瓶颈 |

### 目标

- 召回率 ≥ 90%
- 泛用性（不依赖手工优化）
- 速度快（避免多轮 LLM）

---

## 二、列级别检索深度分析

### 测试的聚合策略

| 策略 | 召回率 | 说明 |
|-----|-------|-----|
| Max Score | **0%** | 取最高分列，失败 |
| 平均分 | 12% | 所有列平均，失败 |
| 累加分 | **50%** | 分数之和，最佳 |
| 加权投票 | 50% | 与累加分相当 |

### 列级别为什么效果差？

| 问题 | 说明 |
|-----|------|
| **语义稀释** | 单列描述太简单（如 `IS_ONLINE` = "是否在线"）|
| **关键词缺失** | 用户问"设备数量"，目标表没有任何列包含"数量" |
| **噪声太多** | 3353 列中有大量不相关列排名靠前 |

### 查询重写测试

| 方案 | 效果 |
|-----|------|
| 跨语言扩展 | ❌ 更差（目标表消失）|
| 多轮 Judge+Annotator | ❌ 第 0 轮就失败 |

**结论**: 查询重写对列级别检索无帮助，反而导致语义稀释。

## 三、表+列融合检索

### 策略设计

```
用户问题
    ↓
┌─────────────────────────────────────┐
│ 并行检索                              │
│   [表级别] Top K → 表候选集           │
│   [列级别] Top N → 累加分聚合 → Top K │
└─────────────────────────────────────┘
    ↓
[融合] 并集（最大化召回率）
    ↓
Top M 表 → 生成 SQL
```

### 参数优化测试

| 配置 | 表级别 | 列级别 | 融合 |
|-----|-------|-------|-----|
| T10 + C200 → 10 | 88% | 50% | **88%** |
| T15 + C200 → 10 | 88% | 50% | 88% |
| T15 + C300 → 15 | 88% | 62% | 88% |
| T20 + C300 → 15 | 88% | 62% | 88% |
| T20 + C400 → 20 | 88% | 62% | 88% |

> **发现**: 融合召回率卡在 88%，瓶颈不是参数配置。

## 四、失败 Case 深度分析

### Case 1（唯一失败案例）

```
问题: 设备ciscoA，上个月发生了几次告警，按告警类型进行分类统计
期望表: ['event_history', 't_bz_config_ci_ne_root']
实际: event_history ✅, t_bz_config_ci_ne_root ❌
```

### `t_bz_config_ci_ne_root` 在表级别的排名

| 排名范围 | 是否出现 |
|---------|---------|
| Top 10 | ❌ 没有 |
| Top 20 | ❌ 没有 |
| Top 30 | ❌ 没有 |

### 为什么找不到？

**问题关键词**: `告警`, `设备ciscoA`, `告警类型统计`

**表描述匹配分析**:

| 表 | 描述关键词 | 匹配度 |
|---|---------|-------|
| `event_history` | 事件历史、告警信息 | ✅ 高 |
| `t_bz_sdn_alarm` | SDN告警 | ✅ 高 |
| `t_bz_config_ci_ne_root` | 网元配置、设备基础信息 | ❌ 低 |

**根因**: 用户想要的是"**设备的告警统计**"，需要关联 `event_history`（告警数据）和 `t_bz_config_ci_ne_root`（设备主数据）。

但问题描述更偏向"告警"，所以检索到告警相关表，而没有检索到设备主表。

## 五、重要发现：混合搜索模式

### 问题发现

经检查发现，**当前使用的是 Dense（稠密向量）模式，未启用混合搜索！**

```python
# 当前代码只使用 Dense 向量
embedding = output['dense_vecs'][0]  # 只取 dense
```

### BGE-M3 支持的三种模式

| 模式 | 说明 | 适用场景 |
|-----|------|---------|
| **Dense** | 稠密向量（1024维）| 语义理解 |
| **Sparse** | 稀疏向量（类似 BM25）| 关键词精确匹配 |
| **Multi-vector** | ColBERT 风格 | 细粒度匹配 |

### 混合搜索的潜在价值

对于 Case 1 "设备ciscoA，上个月发生了几次告警"：
- **Dense 模式**：基于语义，找"告警"相关表
- **Sparse 模式**：基于关键词"ciscoA"，可能匹配到设备表中的样本数据

**已实现混合搜索支持**（`BGEM3Embedding.py`）:
```python
# 混合分数 = 0.7 * Dense + 0.3 * Sparse
hybrid_score = dense_weight * dense_score + sparse_weight * sparse_score
```

### 待验证

混合搜索需要重新构建向量索引，因为：
1. 当前索引只存储 Dense 向量
2. 需要同时存储 Sparse 向量
3. LlamaIndex VectorStoreIndex 不直接支持混合搜索

## 六、结论与建议

### 当前最佳方案

| 配置 | 值 |
|-----|---|
| 表级别 Top K | 10 |
| 列级别 Top K | 200 |
| 聚合策略 | 累加分 |
| 融合策略 | 并集 |
| **召回率** | **88%** |

### 达到 90% 的潜在方案

| 方案 | 可行性 | 说明 |
|-----|-------|-----|
| ✅ **混合搜索** | 已实现代码 | Dense + Sparse，需重建索引 |
| ❌ 扩大 Top K | 已测试无效 | 瓶颈不在参数 |
| ⚠️ 外键关联推理 | 可能有效 | 检索到 `event_history` → 自动关联 `t_bz_config_ci_ne_root` |
| ❌ 查询重写 | 已测试无效 | 反而更差 |

### 下一步建议

1. **构建混合搜索索引**：同时存储 Dense 和 Sparse 向量
2. **测试混合检索效果**：看 Sparse 模式能否捕获"ciscoA"关键词
3. **考虑外键推理**：如检索到告警表则自动关联设备主表
